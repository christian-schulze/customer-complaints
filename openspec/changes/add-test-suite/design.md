# Design

## Context

See `proposal.md` - Why/What Changes. `classifier-core.workflow.ts` and `router.workflow.ts` (both archived, Changes 1-2) already expose clean sub-workflow contracts: `classifier-core` returns `{ reply, done, result }`; `router` returns `{ referenceId, routes, category?, priority? }` and already supports being called in wait mode (`chat.workflow.ts`'s `CallClassifierCore` node uses `waitForSubWorkflow: true`; `CallRouter` uses `false` for the live fire-and-forget path). This change adds a third caller of both — `test-harness.workflow.ts` — that calls `classifier-core` the same way `chat.workflow.ts` does, but calls `router` with `waitForSubWorkflow: true` instead, since tests need the routing result back, not a fast reply.

Confirmed live: `n8n-nodes-base.webhook` v2.1 supports `authentication: 'headerAuth'` against an `httpHeaderAuth` credential — matches the handoff's "Webhook protected by header auth (`TEST_WEBHOOK_SECRET`)" instruction without needing a hand-rolled check in a Code node.

## Goals / Non-Goals

**Goals:**
- The harness is a thin caller, not a reimplementation: it does not duplicate classification or routing logic, only sequences the two existing sub-workflows and shapes their combined response.
- Tests exercise exactly what users talk to (PRD requirement) — the harness's call to `classifier-core` must be wired identically to `chat.workflow.ts`'s (same input shape, same config-merge behaviour), so a passing test is evidence about the real chat path, not a parallel implementation.
- Config override is a harness-level concern, invisible to `classifier-core`/`router` themselves — neither sub-workflow needs to know it's being tested, and `classifier-core` is not modified by this change at all; `router` gets exactly one small, additive column mapping (see Decisions).
- The runner is a thin HTTP client plus assertion/reporting logic — no test-only duplication of n8n orchestration.

**Non-Goals:**
- Changing `classifier-core.workflow.ts` behaviour, or any of `router.workflow.ts`'s routing/agent logic — this change calls them as-is, with one narrow exception documented under Decisions (a missing column mapping needed for cleanup parity).
- CI integration — explicitly a "Next steps" item in the PRD (§9), not this change.
- Simulated conversations, LLM-as-judge, and repeated-run pass rates (TR-6/7/8) are designed at a lighter level here since they're should-have/time-permitting; if dropped, nothing above them needs to change.

## Decisions

**Harness is a new top-level workflow, not an extra trigger on `chat.workflow.ts`.**
Chat Trigger and Webhook are different trigger node types with different response semantics (the handoff notes "Respond to Chat" doesn't work in sub-workflows, and the test path needs a plain JSON HTTP response, not a chat-formatted one). A dedicated `test-harness.workflow.ts` keeps the production chat path untouched by test-only concerns (header auth, config override), matching the existing pattern of one workflow per entry point.

**Test-generated records are tracked and optionally cleaned up by the runner, not suppressed by the workflows — `router.workflow.ts`'s routing logic is not modified by this change.**
An earlier version of this design had the harness pass a `dryRun` flag through to `router`, with its Switch branches skipping the Data Table insert nodes. Rejected: it would require editing and re-regression-testing `router.workflow.ts`'s branching logic — already built, live-tested, and archived in Change 2 — for a cleanliness concern, not a correctness one, and it would mean tests no longer exercise the real insert path at all. Instead, the runner already receives the exact `referenceId` and destination table(s) `router` returns for every case (per `complaint-routing`'s "Routing result is reportable" requirement), so it records those in its report as it goes. A separate, explicitly-invoked `npm run test:cleanup` command reads the most recent report and deletes exactly those rows via the n8n Data Table REST API (`DELETE` matched on `referenceId`). This gives higher-fidelity tests (the full write path runs for real) at lower implementation cost than the dry-run alternative, at the price of tests leaving real rows behind until cleanup is run deliberately.

**`not_legitimate_log` gains a `referenceId` column; `router.workflow.ts`'s `Write Not Legitimate Log` node gains one column mapping to populate it.**
Discovered while building cleanup: unlike `complaints_register` and `review_queue`, `not_legitimate_log`'s columns (PRD §6.8: timestamp, reasons, summary) have no `referenceId`, so cleanup can't match-and-delete those rows the same way as the other two. Two cleanup-side alternatives were considered and rejected: matching on exact `summary` text plus a client-recorded timestamp window (fragile — depends on the runner's wall-clock window lining up with the server's insert timestamp, and breaks if cleanup runs long after the test session), or excluding `not_legitimate_log` from cleanup entirely (leaves junk behind, documented as a manual step). Christian preferred fixing the actual gap: `Build Not Legitimate Log Row` already computes `referenceId` (classifier-core generates one for every `done: true` result, regardless of label) and passes it through to `Finalize Routing Result` — it was simply never mapped onto the insert node's columns, because the table never had the column to receive it. Adding the column (via a script mirroring `scripts/create-tables.sh`) and one `referenceId` entry in `Write Not Legitimate Log`'s column mapping closes the gap with a single additive field, not new branching logic — a materially smaller, lower-risk change than the rejected `dryRun` redesign. This is a deliberate, approved deviation from PRD §6.8's exact column list, done for test-infrastructure parity; tracked as a `complaint-records` MODIFIED requirement in this change's specs.

**Config override reuses `chat.workflow.ts`'s existing Config node pattern via a merge, not a second config schema.**
The harness's `Config` node is a Code node that takes the same defaults (`insurerName`, `products`, `maxFollowUps`, `confidenceThreshold`) `chat.workflow.ts` uses and shallow-merges any `config` object from the incoming request on top, so a test can override one field (e.g. `confidenceThreshold: 0.99`) without re-specifying the rest. This is the same merge semantics implied by FR-6 and keeps the defaults in one conceptual place (duplicated as literals in both workflows' Config nodes, same trade-off Change 2's design.md already accepted for the tone-rules prompt text — no shared-config mechanism exists across separate `.workflow.ts` files).

**Response shape: a final Code node assembles `{ reply, done, result, routing }`, `responseMode: 'lastNode'`.**
Mirrors `classifier-core`'s own `Finalize Result` pattern (Change 1) rather than a `Respond to Webhook` node with manual JSON — one fewer node, and consistent with how `chat.workflow.ts` already reads `CallClassifierCore`'s output via `$('CallClassifierCore').item.json` rather than trusting `$input` to survive the AI Agent boundary (CLAUDE.md gotcha). The harness's final node reads both `$('CallClassifierCore').item.json` and `$('CallRouter').item.json` explicitly for the same reason.

**Test case fixtures are plain JSON, not TypeScript, under `tests/cases/scripted/`.**
Keeps case authorship and review (TR-9 — Christian reviews before a case counts) simple diffable data, no build step, matching the handoff's repo layout (§2). One file per case for easy individual review/diff, named `<id>.json`.

**Runner is a small TypeScript CLI (`tests/runner/`), no test framework (Jest/Vitest) dependency.**
The behaviour needed — sequential HTTP calls per case, custom pass/fail aggregation, a confusion matrix, Markdown+JSON report generation, non-zero exit — doesn't need a test framework's assertion/mocking machinery, and a framework would fight the "N runs per case, aggregate pass rate" requirement (TR-8) more than it helps. Plain `tsx`/`ts-node` script with `node:test`-free custom runner logic, invoked via `npm test` → `package.json` script.

**Confusion matrix and accuracy are computed only over fields each case declares in `expected`.**
A case that doesn't assert `category` (e.g. a `not_legitimate` case) shouldn't count as failing or passing on a field it never claimed — per-field results are only computed where `expected` has the key, consistent with PRD §7's "Each case asserts **some or all of**" wording.

**Induced-failure cases are authored but kept `disabled: true`, documenting a live finding rather than exercising the path.**
The original plan was a prompt-level trigger: a message engineered to make the Structured Output Parser's `autoFix` give up. Live-tested against both `classifier-core`'s `Classify` agent and `router`'s `Routing Agent` (prompt-injection attempts, malformed config): none broke the schema. The reason is architectural, not a matter of trying harder — `hasOutputParser: true` on an n8n AI Agent node enforces the schema via Anthropic's forced structured output at the API level, not merely by prompt suggestion, so conversational content cannot produce non-conforming output regardless of what it instructs the model to do. The only way to reach either `onError` branch is a genuine API-level failure (invalid credential, rate limit, timeout) — real, but not something a scripted conversation can cause, and not safe to automate into a repeatable `npm test` run (it would need to temporarily break the shared Anthropic credential, briefly affecting live chat traffic too). Christian confirmed a one-time live credential-swap verification wasn't worth the trouble. Both cases are kept in `tests/cases/scripted/` with `disabled: true` and a `disabledReason` field explaining the finding — visible, reviewable record of the attempt, skipped by the runner (zero HTTP calls, excluded from scoring) rather than deleted. Documented in the README.

## Risks / Trade-offs

- **Config defaults are now literal-duplicated across three workflows (`chat`, `classifier-core`'s caller context, `test-harness`)** → Mitigation: already an accepted trade-off per Change 2's design.md for prompt text; documented here for config too. No shared-module mechanism exists between separate `.workflow.ts` files without introducing a build step n8n-as-code doesn't require.
- **Both `onError: continueErrorOutput` branches (classifier-core's `BuildFailureResult`, router's `Routing Agent Failure`) are code-reviewed and architecturally sound but not live-exercised by this suite** → Mitigation: documented explicitly, with the live finding that caused it, in both the disabled case files and the README's "Production considerations" / "Scope & trade-offs" sections, rather than silently left unmentioned.
- **Test runs leave real synthetic rows in the demo Data Tables until cleanup is run** → Mitigation: the runner records exactly which `referenceId`s went where, so `npm run test:cleanup` can remove precisely those rows on demand; cleanup is a separate, explicit, never-automatic command (deleting data is a destructive action and shouldn't be a side effect of `npm test`), and the README documents running it before a demo if a clean table view matters.
- **Should-have items (TR-6/7/8) are time-boxed and may not land** → Mitigation: proposal and tasks.md sequence them strictly after the Must-have bar (TR-5 passing on scripted cases, README written, JSON exported); if time runs out they're dropped and documented under "Next steps" in the README, per PRD §9's own prioritisation.
- **`unknownReason: 'ambiguous'` is not reliably distinguishable from `insufficient_info` through scripted content** → Mitigation: `unknown-ambiguous.json` only asserts `label: unknown`, not the specific reason, after five live-iteration attempts all landed on `insufficient_info` or resolved to a clear label instead; flagged explicitly (not silently narrowed) in the case file's own description, in tasks.md 5.1, and in the README's "Scope & trade-offs" and "Next steps" as a follow-up needing either sharper prompt wording or sharper PRD definitions before it can be pinned in a test.

## Migration Plan

Mostly additive. New files: `workflows/local/test-harness.workflow.ts`, `package.json`, `tests/**`. No changes to `chat.workflow.ts` or `classifier-core.workflow.ts`. One scoped change to `router.workflow.ts`: add `referenceId` to `Write Not Legitimate Log`'s column mapping (`n8nac pull` fresh first, validate, push `--verify`, then re-test the three other Switch branches to confirm no regression, since the file is being touched regardless of how small the diff is). One scoped change to the `not_legitimate_log` Data Table: add a `referenceId` string column via a new idempotent script, run once against the existing table (existing rows get a null/empty `referenceId`, which is fine — they predate this change and aren't part of any test run's cleanup set). Modified: `.gitignore` (`tests/reports/`), `n8n-export/` (regenerated to include the harness), `README.md` (written). Rollback: `git revert` the new files and the `router.workflow.ts` diff; the added Data Table column can be left in place harmlessly or removed via the n8n UI if ever needed. `npm run test:cleanup` removes any test-generated rows left behind.
