# Design

## Context

See `proposal.md` - Why/What Changes. Change 1 (archived) delivered `chat.workflow.ts` and `classifier-core.workflow.ts`, producing `{ reply, done, result }` where `result` is the flat-then-renested classification shape documented in `classifier-core.workflow.ts`'s `Finalize Result` node. This change consumes that unchanged and adds `router.workflow.ts`, plus the three Data Tables it writes to. Confirmed live against the running instance: Data Tables exist on this n8n version (`GET /api/v1/data-tables` returns `{ data: [], nextCursor: null }`, not a 404) and are creatable via `POST /api/v1/data-tables` with typed columns (verified with a throwaway probe table, deleted after).

## Goals / Non-Goals

**Goals:**
- A sub-workflow boundary clean enough that Change 3's test harness can call `router` directly in wait mode and assert on its returned destinations/category/priority, mirroring how it calls `classifier-core`.
- Deterministic routing (FR-7.1) that a Switch node enforces, not prompted judgment — testable without an LLM call, same philosophy as Change 1's confidence-threshold and product-check backstops.
- The complainant-facing path stays fast: routing and table writes happen after the chat reply is already on its way back (FR-7.3), never blocking it.

**Non-Goals:**
- The test harness itself, or wait-mode wiring for tests — Change 3.
- Automating table creation as part of `docker compose up` — Change 4. This change's table-creation script is a manual, re-runnable setup step (same category as Change 1's manually-created Anthropic credential), not yet wired into a bootstrap.
- Any notification or external destination (email, Slack, ticketing) — explicitly out of scope per PRD §3.

## Decisions

**Routing destinations are a Switch node on `result.label` + `result.escalate`, not a single expression per table.**
FR-7.1's five cases collapse to two independent writes (register, review queue) gated by different boolean combinations, plus a third mutually-exclusive case (not-legitimate log). Modeled as a 4-output Switch (`register-only`, `register+queue`, `queue-only`, `log-only`) rather than three independent If nodes, so the routing map stays legible as one node and matches the handoff's "Switch per PRD FR-7.1" instruction directly. `legitimate`+escalated is its own output (not two separate fan-outs from two different conditions) so both writes are guaranteed to use the same evaluated record, not risk divergent re-evaluation.

**Routing agent runs only on the Switch's legitimate outputs, as a second stage, not inline in the Switch.**
The Switch decides destinations first (pure data comparison); the routing agent (AI Agent + Anthropic Chat Model + Structured Output Parser, no tools, no memory — each invocation is a single judgment on a finished, complete record, not a multi-turn conversation) runs afterward only on the branches carrying `legitimate`. This keeps the deterministic/judgment boundary exactly where Change 1 drew it for the classifier: routing nodes decide branching, LLMs only judge inside a node.

**Routing agent schema is flat, following Change 1's discovered constraint.**
Change 1's design.md recorded that nesting a Structured Output Parser's required fields under a sub-object made Claude intermittently drop fields with no thrown error. The routing agent's parser schema (`category`, `priority`, `acknowledgementDraft`) stays flat for the same reason; a `Finalize Routing Result` Code node assembles the final `{ referenceId, routes, category, priority }` shape, mirroring `classifier-core`'s `Finalize Result` pattern.

**Acknowledgement draft is generated by the routing agent, not a second call to the classifier.**
FR-5.2 requires it only for `legitimate` complaints, and the routing agent already has the full `result` (summary, extracted fields, tone) available as input — no second LLM round-trip needed. The tone rules and FR-5.4 prohibitions are restated in the routing agent's system prompt exactly as worded in `customer-messaging`'s spec (shared source of truth, duplicated text — these are two different nodes with no connection between them, so the rules have to live in both prompts; a future refactor could extract a shared prompt fragment if n8n-as-code supports it, but that's not worth the time here).

**Table creation: a script using the n8n REST API, run once manually, not a workflow node.**
The Data Table node's `insert` operation requires an existing `dataTableId` — it has no "create if missing" operation reachable from a workflow. Creating the three tables is therefore a one-off setup action, exactly like Change 1's manually-created Anthropic credential and n8n API key. Implemented as a small script (`scripts/create-tables.ts` or `.sh`) using `N8N_API_KEY` from `.env`, calling `POST /api/v1/data-tables` for each table with its typed columns, and checking `GET /api/v1/data-tables` first so a re-run doesn't error or duplicate. This also lays groundwork directly reusable by Change 4's bootstrap.

**Table columns, typed per PRD §6.8:**
- `complaints_register`: `referenceId` (string), `timestamp` (string, ISO), `summary` (string), `extracted` (string, JSON-encoded — Data Table columns are flat-typed, no native object/array column type confirmed from the node schema), `category` (string), `priority` (string), `customerTone` (string), `acknowledgementDraft` (string), `escalated` (boolean).
- `review_queue`: `referenceId` (string), `timestamp` (string), `label` (string), `reason` (string), `summary` (string), `transcript` (string, JSON-encoded array).
- `not_legitimate_log`: `timestamp` (string), `reasons` (string, JSON-encoded array), `summary` (string).

**`router` receives the classifier's full output plus `config`, not a re-derived subset.**
`chat.workflow.ts` passes `{ result, config }` (the same `config` object already in scope) to `router` via Execute Workflow, so the routing agent's prompt can read `insurerName` the same way the classifier's prompt does (FR-6.2) without re-fetching configuration.

**Fire-and-forget call: `waitForSubWorkflow: false` on `chat.workflow.ts`'s Execute Workflow node calling `router`.**
Mirrors the `waitForSubWorkflow: true` option already used for the `classifier-core` call in Change 1 — same node type, opposite setting, confirmed as a documented option on `executeWorkflow` v1.3 (`npx n8nac skills node-info executeWorkflow`). `chat.workflow.ts`'s `Format Chat Response` node continues to read only `classifier-core`'s output; the router call is wired as an additional, parallel branch off the `done == true` path, not inserted into the reply's own chain.

## Risks / Trade-offs

- **Data Table columns have no native array/object type** (unconfirmed otherwise from `npx n8nac skills node-info dataTable`) → Mitigation: JSON-encode `extracted`, `transcript`, `reasons` as strings; acceptable for a Data Table meant to be read by a human in the n8n UI or re-parsed by a future test assertion, not queried by column.
- **Duplicated tone-rules prompt text between `classifier-core` and the routing agent** → drift risk if one is edited without the other. Mitigation: noted above; both prompts cite the same `customer-messaging` spec requirements by name as a comment, so a future editor sees the link.
- **Fire-and-forget routing means a routing failure is invisible to the complainant and to the chat workflow** → Mitigation: `router`'s own Code node records a failure outcome into `review_queue` (reusing the "never fail silently" principle from Change 1) rather than throwing silently; full exercising of this path is a Change 3 test-harness concern (it runs `router` in wait mode specifically so test assertions can see routing failures that the live chat path can't).
- **Manual table creation script must be re-run after a fresh `docker compose up` with a new volume** → Mitigation: documented in the README's manual setup section (already planned as a must-have); the check-before-create logic avoids errors on a second run against an existing volume.

## Migration Plan

Additive — `classifier-core.workflow.ts` and its external contract are unchanged. New file `router.workflow.ts` is created, validated, and pushed. `chat.workflow.ts` is pulled fresh, the router call added, validated, and pushed with `--verify`. Tables are created via the new script against the running instance before testing the routed paths live. Rollback: `git revert` the `.workflow.ts` changes and re-push; dropping the three Data Tables (if ever needed) is a manual UI/API action, not scripted, since nothing currently depends on removing them.
