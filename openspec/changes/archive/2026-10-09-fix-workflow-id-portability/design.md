# Design

## Context

See `proposal.md` - Why/What Changes for the problem and the constraint it establishes (resolved, instance-specific workflow IDs must never be written into git-tracked `.workflow.ts` source). Additional context gathered live this session, not yet written anywhere else:

- n8n has no way for a caller to choose a workflow's ID on creation, whether via `n8nac push`'s create-fallback or n8n's own JSON import - a brand-new workflow always gets an ID n8n mints itself. This is the root cause: `chat`'s and `test-harness`'s Execute Workflow nodes hardcode `classifier-core`'s/`router`'s workflow ID, and that ID is never portable across a fresh creation.
- `workflows/local/*.workflow.ts` is this project's single source of truth (CLAUDE.md). `n8n-export/*.json` (`scripts/export.sh`) is a generated export artifact for reviewers who want to inspect the JSON - it has never been, and must not become, a documented way to *load* the workflows onto an instance. The only documented load path is `npx n8nac push <file>.workflow.ts --verify` for each of the four files.
- n8n's "Variables" feature (`$vars.X`, which would otherwise be the standard way to decouple a cross-workflow reference from a literal ID) returns `403 "Your license does not allow for feat:variables"` on this instance - confirmed live, not available here.
- The Execute Workflow node's `workflowId` resource-locator has three *input* modes - `id` (paste the ID), `list` (pick from a dropdown, storing a `cachedResultName` for display), `url` (paste the workflow's URL) - but all three resolve purely via the stored `value` (the ID) at execution time; none of them re-resolve by name at runtime. Confirmed live with a throwaway probe (two workflows: a caller and a callee), per CLAUDE.md's "test live, not guess" convention: deleted the callee and recreated it under the same name with a new ID, then set the caller's node to `mode: 'list'` with `value` left pointing at the old, deleted ID but `cachedResultName` correctly set to the callee's real, current name. Execution still failed - n8n never looked the name back up. `cachedResultName` is write-only display metadata, not a fallback lookup key. This rules out any "use a different `mode`" alternative to Decision 1's by-name API lookup; Variables is the only genuine by-name indirection n8n offers, and it's unavailable here.
- `n8nac promote` remaps Execute Workflow references and credentials between two *configured n8nac environments*, storing the resolved bindings in `n8nac-promotion.json` (separate from workflow source) - architecturally the right idea, but it's built for genuinely distinct, concurrently-existing environments (dev/stage/prod). This project has one environment (`openspec/config.yaml`: "Single environment: Local... The separate n8n.cmonkey.me instance is not used for this project"). A live `--dry-run` also hit an unresolved credential-binding blocker. Pulling in `promote` for a single-instance wipe-and-rebuild problem would mean standing up a second environment definition and a promotion-config file this project has no other use for, to solve a problem that doesn't involve two environments.
- n8n's workflow-activation check enforces dependency order at the API level, not just in the UI: activating `chat` or `test-harness` before `classifier-core`/`router` are active fails with "Cannot publish workflow: ... references workflow X which is not published." Confirmed live, repeatedly. Likewise, `DELETE /workflows/:id` on an active workflow fails with "Cannot delete a published workflow. Unpublish it before deleting." - deactivate before delete, every time.
- The n8n workflow-update API is a full `PUT` of the workflow definition, not a partial patch - updating two node parameters means fetching the live definition, changing just those two values in memory, and writing the whole thing back. Confirmed live which fields the `PUT /workflows/:id` body must exclude: `id`, `active`, `activeVersion`, `activeVersionId`, `createdAt`, `isArchived`, `meta`, `nodeGroups`, `shared`, `sourceWorkflowId`, `tags`, `triggerCount`, `updatedAt`, `versionCounter`, `versionId` are all read-only (the request 400s if present), and a `description: null` is rejected outright (must be omitted, not nulled) - but omitting `active` entirely on a `PUT` leaves the workflow's current active/inactive state untouched, which is what makes a no-op-when-unchanged correction safe.
- Activation and deactivation are separate, idempotent endpoints: `POST /workflows/:id/activate` and `POST /workflows/:id/deactivate`, both returning 200 whether or not the workflow's state actually changes.
- `npx n8nac push <file>.workflow.ts` writes the newly-created remote ID back into the local `.workflow.ts` file's own `@workflow({ id: ... })` decorator (along with `active: false` and dropping `projectId`) whenever the file's previously-committed `id` no longer resolves on the target instance - this is `n8nac`'s own create-fallback behavior, not something this change's script does or can suppress. Confirmed live: after deleting all four workflows and re-running `n8nac push` on each file, `git diff workflows/local/` showed exactly these three fields changed, nothing else. This is an accepted, pre-existing limitation of using `n8nac push` as the (now sole) load path on a genuinely wiped instance - treat it the same as the already-documented `n8nac pull` noise (see Risks) and discard it before committing. It is orthogonal to this change's own requirement that *the deploy-correction script* never touches tracked source - confirmed separately, with a before/after diff isolating the script's own run.

## Goals / Non-Goals

**Goals:**
- The four workflows can be loaded onto the project's Local instance from any starting state and end up fully correct and active, satisfying `specs/workflow-deployment/spec.md`.
- Git-tracked `.workflow.ts` source never needs an instance-specific edit as part of running the deploy-correction script itself.
- Loading the workflows has exactly one documented path: `n8nac push` from the git-tracked `.workflow.ts` source. No JSON-import instructions remain in the README.

**Non-Goals:**
- Full zero-touch bootstrap (credential creation, Data Table creation, activation, all triggered by `docker compose up` with no commands run) - that's the separate, still-not-attempted `add-auto-bootstrap` PRD item (PRD line 230). This change only fixes the workflow-loading step's correctness.
- True multi-environment promotion (`n8nac promote` between distinct environments). Out of scope per the single-environment project context; revisit only if the project ever gains a second, concurrently-existing n8n environment.
- Changing how the Anthropic or webhook credentials are created on the instance. The design does add a check that they exist (see Decisions), but creating them is unchanged from the current manual-UI-and-script steps.
- Making `n8nac push`'s local-file-rewrite side effect (see Context) disappear. That's a pre-existing property of the tool this project already uses for every workflow edit, not something introduced or fixable by this change; it's handled by the same "discard before committing" convention as the existing `n8nac pull` noise.

## Decisions

### 1. Correct the two cross-workflow references with a post-load, out-of-band API update - never by writing into tracked source

After the four workflows exist on the instance (loaded via `n8nac push` - see Decision 3), a script:
1. Looks up `classifier-core`'s and `router`'s current workflow IDs from the live instance by name, via the n8n REST API.
2. Fetches `chat`'s and `test-harness`'s current full workflow definitions, updates only the two Execute Workflow nodes' `workflowId.value` fields in memory to the IDs from step 1, and writes each definition back via the n8n API - skipping the write entirely for a workflow whose nodes already match, so a no-op run touches nothing.
3. Activates `classifier-core` and `router`, then `chat` and `test-harness` (dependency order - see Decision 2).

This never reads or writes `workflows/local/chat.workflow.ts` or `test-harness.workflow.ts` for those two fields. Whatever value is committed there for `workflowId.value` is inert - it only matters as the value `n8nac push` uploads on first load, and this script overwrites it immediately after. It can stay fixed forever.

**Alternatives considered:**
- **(Tried and rejected this session) Write the resolved ID back into the tracked `.workflow.ts` files, then `n8nac push` them again.** Proven to work end-to-end, including a full test-suite pass, but fails the core requirement: every redeploy produces a permanent, meaningless git diff. This is the approach this change replaces.
- **n8n Variables.** Would be the cleanest fix (the Execute Workflow node reads `$vars.CLASSIFIER_CORE_ID` at runtime, set once per instance) - ruled out, not licensed on this instance.
- **Use the Execute Workflow node's `list`/`url` resource-locator mode instead of `id`, relying on the cached name to re-resolve.** Ruled out - confirmed live (see Context) that `mode: 'list'` still executes via the stored `value` (ID), not the `cachedResultName`. There is no mode that performs by-name resolution at runtime; this isn't a simpler alternative to the API lookup, it's the same problem with an extra field that does nothing at execution time.
- **n8nac promote.** Architecturally closest to "right," but built for cross-environment promotion the project doesn't have a second environment for, and its credential-binding path wasn't fully resolved live. Revisit if that changes.
- **Commit a placeholder value, render a substituted copy at deploy time, push the rendered copy instead of the tracked file.** Rejected: the project's standing convention (CLAUDE.md) is `n8nac pull <id>` before editing a workflow, which mirrors whatever is live back into the tracked file - the first pull after a deploy would overwrite the placeholder with the real resolved ID anyway, reintroducing the same churn one `n8nac pull` at a time instead of one `n8nac push` at a time. Avoiding that would mean taking `chat`/`test-harness` out of the normal pull/push convention entirely, a bigger change to how this repo does n8n-as-code than this problem justifies.

### 2. Dependency order is enforced by the script, not left to the operator

`classifier-core` and `router` are activated before `chat` and `test-harness`, every time, because n8n's activation check rejects the reverse order. The script does this itself rather than documenting it as a manual step to remember (the original README already had this as an undifferentiated "activate all four" step, which is exactly the kind of manual step this change exists to remove). The script also checks each workflow's current active state before calling `activate`, so a workflow that's already active is left alone rather than re-activated pointlessly.

### 3. `n8nac push`, from the git-tracked `.workflow.ts` source, is the only documented load path

`workflows/local/*.workflow.ts` is this project's single source of truth; `n8n-export/*.json` is a generated export artifact (`scripts/export.sh`) for reviewers who want to inspect the JSON, not an input to loading an instance. The README's Quick Start therefore documents only `npx n8nac push <file>.workflow.ts --verify` for each of the four files, and drops the old "import from `n8n-export/*.json`" step and its paired "reattach credentials on the imported workflows" step entirely - they are not kept as a fallback for reviewers without `n8nac` configured.

This also simplifies Decision 1's script: it only ever needs to resolve `classifier-core`'s/`router`'s current ID by name and correct the two references after a `push` - there's no second load method it has to stay agnostic to. (The script's name-based resolution would, as a side effect, also work if someone imported JSON anyway - it doesn't inspect how a workflow got onto the instance - but that's incidental, not a path this project tests, documents, or recommends.)

**Alternatives considered:**
- **Document both `n8nac push` and JSON import as equally valid load paths, with the script running after either.** This was the original framing and was implemented, then reverted: it keeps JSON import as a documented fallback for reviewers without `n8nac` configured, consistent with `n8n-export/*.json` existing at all. Rejected per explicit project direction: `workflows/local/*.workflow.ts` is the sole source of truth, and `n8n-export/*.json` must read as a generated artifact *of* a correct deployment, never an *input* to one - presenting it as an alternative load path blurs that line and risks a reviewer loading stale or hand-edited JSON instead of the tracked source.

### 4. Missing credentials are checked and reported before activation is attempted

Per `specs/workflow-deployment/spec.md`'s "missing prerequisites" requirement: before activating, the script checks that the Anthropic credential and the test-harness webhook credential exist on the instance (by name, via the same credentials-list API call already needed elsewhere), and fails with a clear message naming the missing credential and which workflow needs it, rather than leaving a workflow silently inactive.

## Risks / Trade-offs

- **[Risk] Name-based lookup is ambiguous if two workflows share a name** (e.g. two workflows both named "Router") → the script fails loudly listing all matches, rather than guessing which one is correct. Not expected in normal use (n8n doesn't enforce unique names, but nothing in this project's workflow creates duplicates under normal operation).
- **[Risk] A future unrelated edit to `chat.workflow.ts`/`test-harness.workflow.ts` via the standard `n8nac pull <id>` → edit → `push` loop (CLAUDE.md's documented editing convention) will pull the live, currently-correct, instance-specific ID for those two fields back into the tracked file** → this is a real, accepted limitation, not a violation of this change's spec: the spec's "tracked source unaffected" requirement is scoped to a *deploy-correction-script* run, not to the pre-existing edit convention. Mitigation: when pulling either file for an unrelated edit, treat a diff on only the two `workflowId.value` fields as expected noise to discard before committing, same as the `active`/`versionId` fields n8nac pull already tends to touch.
- **[Risk] `n8nac push`'s own create-fallback rewrites the local file's `id`/`active`/`projectId` fields whenever the committed ID is stale (see Context)** → same shape of risk as above, triggered by `push` instead of `pull`, inherent to using `n8nac push` as the load path on a wiped instance. Mitigation: identical - discard as expected noise before committing. This is a direct consequence of Decision 3 (making `n8nac push` the sole load path) and is accepted as part of that trade-off.
- **[Risk] The API-level update in Decision 1 bypasses `n8nac`'s own schema validation path** → mitigate by running `n8nac verify <id>` against `chat` and `test-harness` after the update, confirming the result still validates against the bundled schema, rather than trusting the raw API response alone.

## Migration Plan

The Local instance currently holds four workflows (from this session's live testing) whose committed source no longer matches - expected, not a problem this change needs to fix retroactively, since the new script's first run will re-resolve and correctly wire them regardless of their current state (idempotent per the spec's redeployment requirement). No data migration is needed; this is a tooling-only change. Rollback, if the new mechanism has a defect: the previous process (manually reselecting credentials and hand-fixing the two Execute Workflow node references in the n8n UI after `n8nac push`) still works as a fallback with no change to n8n itself - reverting is a pure revert of the README/CLAUDE.md/script changes.
